# Project environments

`pisbx` gives a project a reproducible pi environment, in the same spirit as a
Python virtualenv managed by `uv`.

```
project/
  pisbx.toml                 # manifest (human, committed)
  pisbx.lock                 # exact versions (machine, committed)
  pisbx.pnpm-lock.yaml       # transitive versions (machine, committed)
  .pisbx/
    env/                     # disposable, ignored by git
      settings.json          # generated: global settings minus packages
      npm/                   # installed extensions
      base/                  # copy of borrowed global config
      extensions -> base/extensions
      statusline -> base/statusline
      AGENTS.md -> base/AGENTS.md
      sessions -> ~/.pi/agent/sessions
      auth.json              # runtime only, never committed
```

`rm -rf .pisbx/env && pisbx sync` reproduces it.

## The four kinds of file

| Kind | Examples | How it is stored | Why |
|---|---|---|---|
| **Owned** | `settings.json`, `npm/node_modules`, `package.json` | real files | reproducible from the lock |
| **Borrowed** | `extensions/`, `statusline/`, themes, skills, rules, prompts, `AGENTS.md`, `SYSTEM.md`, `mcp.json` | copied into `base/`, exposed with **relative** symlinks | relative links survive being mounted at `/home/node` |
| **Runtime** | `auth.json` | created per run, removed on exit | never in the repo or the lock |
| **Shared** | sessions | absolute link on the host, bind-mounted in containers | session keys differ inside a container |

The important rule: **no absolute host symlinks inside the environment.** They look
correct on the host and break as soon as the environment is mounted elsewhere.

## Manifest and lock

`pisbx.toml` is generated by `migrate`, `export`, `add`, and `remove`:

```toml
[pi]
version = "1.5.0"

[extensions]
"npm:@reedchan/statusline" = "1.11.3"
"npm:pi-effort" = "0.1.1"
```

`pisbx.lock` holds the same data as JSON for tooling. `pisbx.pnpm-lock.yaml` pins
transitive dependencies so two machines resolve the same tree.

## Why pnpm

Installs go through pnpm with a shared content-addressable store:

- `auto-install-peers=false` — host-provided packages (`@earendil-works/*`,
  `typebox`) must not be duplicated; pi warns when they are
- `strict-peer-dependencies=false` — no peer resolution failures
- `ignore-scripts=true` — no lifecycle scripts run during sync
- `--prefer-offline` by default, `--offline` with `PISBX_OFFLINE=1`

Measured with eight real extensions:

| Operation | Time |
|---|---|
| cold sync (empty store) | ~8.5s |
| warm sync (rebuild environment) | ~0.65s |
| startup in a container with the environment mounted | ~0.6s, **zero install** |

The environment is bind-mounted into the container or VM, so boxed sessions
normally install nothing. For an extension added *inside* a box, mount the store
too; `sync`/`add` can then link from it instead of hitting the network.

## Migrating a global setup

```bash
pisbx migrate --dry-run     # inventory: extensions, interface files, auth entries
pisbx migrate --register    # adopt everything and register keys
pisbx migrate --keep-auth   # do not rewrite auth.json
```

`migrate` reports every extension with its version, every interface file, and
every credential, then writes the manifest and builds the environment.

## Adding and removing

```bash
pisbx add pi-effort          # shorthand for npm:pi-effort
pisbx add @scope/pkg@1.2.3
pisbx remove npm:pi-effort
pisbx sync                   # rebuild from the lock
```

`add` resolves the current version when omitted, updates the lock, rewrites the
manifest, and re-syncs. Warm sync is sub-second.
